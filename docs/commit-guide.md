# Commit guide

How to write commits and name branches in this repository. A hook rejects what breaks these rules, and CI rejects it again on the pull request.

## Messages

`type(scope): subject`, or `type: subject` for a change that spans the repository.

- **Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- **Scopes:** `tokens`, `styles`, `angular`, `icons`, `metadata`, `schematics`, `mcp-server`, `eslint-plugin`, `stylelint-plugin`, `docs`, `workbench`, `e2e`, `repo`, `ci`, `deps`.
- **Header:** at most 72 characters, imperative, lowercase after the colon, no trailing period.
- **Body:** none, unless a reader could not otherwise understand the change; then a blank line and at most two lines.
- **Trailers:** none. No `Co-Authored-By`, no "generated by" and no tool or model name.
- **Say what changed,** not why it was done.

Messages git writes itself, for merges, reverts, fixups and squashes, pass unchanged.

### Right and wrong

| Wrong                                                    | Right                                                     | Why                                                                   |
| -------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------- |
| `Update files`                                           | `docs(repo): record workspace commands and versions`      | Say what changed                                                      |
| `docs(repo): Add the commit guide.`                      | `docs(repo): add the commit guide`                        | Lowercase after the colon, no period                                  |
| `chore(marketing): tidy the copy`                        | `docs(repo): tidy the readme wording`                     | `marketing` is not a scope                                            |
| `fix: various fixes`                                     | `fix(tokens): use the dark surface role for table rows`   | Name the change                                                       |
| `docs(repo): clean up before sending the repository out` | `docs(repo): remove third-party references from the spec` | Describe the change, not the reason, and keep the rules on disclosure |

The first three wrong messages are rejected by a hook. The last two pass it: vagueness and reason-framing are caught by the author and the reviewer, not by a check.

A trailer is a rule of its own:

```
docs(repo): add the commit guide

Co-Authored-By: Someone <someone@example.com>
```

is rejected; the same message without the trailer passes.

### One commit, one concern

A commit holds one decision, so `git log`, `git blame`, `git bisect` and a single-commit revert stay reliable.

Three rules have no check and rest on the author and the reviewer: one concern per commit, imperative mood, and saying what changed rather than why. Everything else above is enforced.

A task that adds Prettier and reformats every existing file is two concerns:

```
build(repo): add prettier as the formatter     # the config and the dependency
style(repo): format existing files with prettier   # the reformatting
```

Reviewing the first is then a matter of reading eight lines instead of hunting them inside a thousand.

## Branches

- **Spec work:** `NNN-slug`, the same as the spec folder, for example `002-commit-rules`.
- **Anything else:** `type/slug`, for example `fix/tokens-dark-contrast`. The slug usually starts with a scope.
- **Shape:** lowercase, hyphen-separated, at most 50 characters.
- **No person, company or tool name.** A `claude/` prefix is tool attribution; rename such a branch before the first push.
- One branch per pull request, deleted after merge. A pull request for a spec names its spec folder.

## Disclosure

Messages, branch names and pull request text are public and permanent.

- No company or client names, no recruiter, interview, application or portfolio framing, no possessive framing about an employer.
- Name the domain, not the employer.
- Generic vocabulary is checked from `tools/commit-rules/disclosure-patterns.mjs`, which is committed. Proper nouns go in `.disclosure-terms.local`, which `npm install` creates from `.disclosure-terms.example` and git never sees. CI reads the same names from a repository secret.
- A failure names the rule and the commit, never the term, so no log leaks a name.

## How it is enforced

| When                       | What happens                                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| An agent proposes a commit | A Claude Code hook checks the message before git runs and gives the agent the broken rules                      |
| You commit                 | The `commit-msg` hook rejects a bad message; a fix costs one retype                                             |
| You push                   | The `pre-push` hook checks the branch name and every outgoing commit, including commits made with `--no-verify` |
| You open a pull request    | CI runs the same checks, for clones where the hooks were never switched on                                      |

The hooks are switched on by `npm install`. Only the CI check cannot be bypassed.

To check something by hand:

```bash
node tools/commit-rules/check-message.mjs - <<< "docs(repo): add the guide"
node tools/commit-rules/check-branch.mjs 002-commit-rules
```
