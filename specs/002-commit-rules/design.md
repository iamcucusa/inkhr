# 002 Commit rules: design

## The rules

This section is the source the checkers and `docs/commit-guide.md` are written from.

### Messages

| Rule         | Detail                                                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Format       | Conventional Commits, `type(scope): subject` or `type: subject`                                                                                                                                                       |
| Types        | `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`                                                                                                                          |
| Scopes       | `tokens`, `styles`, `angular`, `icons`, `metadata`, `schematics`, `mcp-server`, `eslint-plugin`, `stylelint-plugin`, `docs`, `workbench`, `e2e`, `repo`, `ci`, `deps`; omitted for a change that spans the repository |
| Header       | At most 72 characters, imperative, lowercase after the colon, no trailing period                                                                                                                                      |
| Body         | None, unless a reader could not otherwise understand the change; then a blank line and at most two lines                                                                                                              |
| Trailers     | None: no `Co-Authored-By:`, `Signed-off-by:`, `Generated with`, `Generated by`, or a tool or model name with a version                                                                                                |
| Content      | Say what changed, not why it was done, and not "improve docs" or "various fixes"                                                                                                                                      |
| Pass through | Messages git writes itself: `Merge ...`, `Revert "..."`, fixup and squash                                                                                                                                             |

"Concrete" and "one commit, one concern" cannot be checked. The workflow carries them: an agent stops after each task and proposes the message, and the maintainer approves.

### Branches

| Rule         | Detail                                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Spec work    | `NNN-slug`, the same as the spec folder, for example `002-commit-rules`                                                          |
| Other work   | `type/slug`, with a type from the table above; the slug usually starts with a scope, as in `fix/tokens-dark-contrast`            |
| Shape        | Lowercase, hyphen-separated, at most 50 characters                                                                               |
| Names        | No person, company or tool name; a `claude/` prefix is tool attribution and an agent renames such a branch before its first push |
| Pass through | `main` and `changeset-release/*`                                                                                                 |

### Disclosure

Commit messages and branch names are public and permanent, so they carry the same rule as files: no company or recruiter names, no interview, application or portfolio framing, and no possessive framing about an employer. Name the domain, not the employer.

## Disclosure without upkeep

Two lists, one committed and one private, so nobody maintains a vocabulary by hand.

- **`tools/commit-rules/disclosure-patterns.mjs`, committed.** The generic vocabulary: `recruiter`, `recruiting`, `interview`, `hiring manager`, `take-home`, `coding challenge`, `assessment`, `candidate`, `applicant`, `application`, `job offer`, `cv`, `resume`, `portfolio`, `screening`, `my employer`, `the client`, `their stack`. Matching is case-insensitive, on word boundaries, and each entry also matches its `s`, `es` and `'s` forms, so plurals and possessives never have to be added. Words with an innocent second meaning (`application`, `assessment`) match only outside a code span, because a message about an app is not a disclosure slip.
- **`.disclosure-terms.local`, never committed.** Proper nouns only, one per line, `#` for comments: company names, product names under NDA, people's names. This is the list that would be sensitive, and it stays out of git.
- **`.disclosure-terms.example`, committed.** The same format with fictional placeholders, and the file the private list is created from.

The private list is created by `npm install`: the `prepare` script copies the example to `.disclosure-terms.local` when that file is missing, and never overwrites it. Without the file the pattern check still runs, and the checker prints one notice; it never fails for a missing list.

Failures name the commit and the rule, never the matched text, so a log never leaks a private name.

## Layers

Each layer calls the same two checkers.

| Layer              | File                                                                                               | What it does                                                                                                                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent, before git  | `.claude/settings.json` `PreToolUse` on `Bash`, running `tools/commit-rules/claude-pre-commit.mjs` | Extracts the message from a `git commit` command (`-m` values or a heredoc), checks it, and exits 2 with the broken rules on stderr. A message it cannot extract passes through to `commit-msg` |
| Agent, bypass      | `.claude/settings.json` `permissions.deny`                                                         | the no-verify forms of `git commit` and `git push`, each listed in both the `cmd:*` and the `cmd*` form so the rule holds across Claude Code versions                                           |
| Agent, attribution | `.claude/settings.json` `attribution`                                                              | `{"commit": "", "pr": ""}`, so no trailer is added. `includeCoAuthoredBy` is deprecated                                                                                                         |
| Commit             | `.githooks/commit-msg`                                                                             | Runs the message checker on the message file                                                                                                                                                    |
| Push               | `.githooks/pre-push`                                                                               | Runs the message checker on every outgoing commit and the branch checker on the pushed branch, catching commits made before the hooks were on                                                   |
| Pull request       | `.github/workflows/checks.yml`                                                                     | The binding layer: re-runs both checkers and `npm run format:check`                                                                                                                             |

`pre-commit` keeps its `lint-staged` step and gains nothing here: the affected lint, test and type-check steps arrive with the first project.

Only CI cannot be bypassed: `.claude/settings.json` reaches Claude Code users and a user's own settings can override it, and git hooks are off until `npm install` runs. Every rule therefore lives in the checkers and in `docs/commit-guide.md`, never only in Claude Code settings.

## CI

One workflow, `checks`, on `pull_request`, with `actions/checkout@v7` at `fetch-depth: 0` and `actions/setup-node@v7` on Node 24 with npm caching. It runs `npm ci`, then the branch check on the head branch, `check-range.mjs` over the pull request's commits, `npm run format:check` and `npm test`.

The private terms reach CI as the repository secret `DISCLOSURE_TERMS`, one per line, written to a temporary file the checker reads and never printed. A pull request from a fork gets no secret: the pattern check still runs, and the job says the private list was skipped.

Rebase merges keep each checked commit, so the pull request title needs no check. If squash merges are ever enabled, `github-setup.md` adds one.

## Decisions

- **Vitest 5.0.1 now**, rather than Node's runner, so the repository has one test command from the start and the first package inherits it. It is the runner `docs/stack-and-dependencies.md` already names.
- **No commitlint.** The header rules are a small regular expression, and the trailer and disclosure checks would stay custom anyway, so one checker is less to keep in step.
- **Node, no dependencies, in `tools/`**, so the same scripts run from Claude Code, from git hooks and from CI.
