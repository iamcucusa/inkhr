# Commit rules: what they are and how to enforce them

Hand-over for the first code session in this repository. Nothing here is implemented yet. Work through the steps in order, one commit per step, following the rules below from the very first commit.

Why this exists: rules written only in `CLAUDE.md` or `AGENTS.md` are advice. Long sessions get compacted, subagents start with little context, and Claude Code adds a `Co-Authored-By` trailer by default. The rules survive only when they are always in view and a check blocks a bad commit before it exists.

## The rules

### Commit messages

- **Format:** Conventional Commits, `type(scope): subject`, the usual standard for design system libraries and the one Changesets and changelogs read well.
  - Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
  - Scopes are package or area names: `tokens`, `styles`, `angular`, `icons`, `metadata`, `schematics`, `mcp-server`, `eslint-plugin`, `stylelint-plugin`, `docs`, `workbench`, `e2e`, plus `repo`, `ci` and `deps` for repository-wide changes. A scope may be left out for a change that spans the whole repository.
- **Subject only.** No body, unless a reader, human or agent, could not otherwise understand the change, and then two lines at most.
- **Shape:** under 72 characters, imperative mood, lowercase after the colon, no trailing period.
- **Concrete:** say what changed. Not "improve docs" or "various fixes".
- **Describe the change, not the reason.** "docs: remove third-party references from spec" is right; "docs: clean up before sending repo to recruiter" is exactly what these rules exist to prevent.
- **No trailers.** No `Co-Authored-By`, and no "generated by" or tool attribution. Model-version trailers read as stale.
- **Messages are public and permanent,** so the disclosure rules apply to them too.

### Disclosure (public repositories)

- No company names, recruiter names, interview or application references, or portfolio framing, in files or in commit messages.
- Name the domain, not the employer. Watch for possessive framing ("their stack", "the client asked for").
- The real list of terms to block lives in `.disclosure-terms.local`, which is gitignored. Only `.disclosure-terms.example`, with fictional placeholders, is committed.

### How commits are made

- **Incremental, atomic, non-breaking.** One task, one commit, one concern. If a task covers two unrelated concerns, split it and say which files go in each. Every commit is self-contained and leaves the repository working, so history reads as one decision per commit and `git log`, `git blame`, `git bisect` and single-commit reverts stay reliable.
- **The quality checks pass before every commit.**

### Branches and pull requests

- **Spec work:** the branch is named exactly like its spec folder, `NNN-slug`, for example `001-nx-workspace`.
- **Other work:** `type/scope-slug`, with a type and scope from the commit rules, for example `fix/tokens-dark-contrast` or `build/deps-angular-22-2`.
- **Shape:** lowercase, words joined by hyphens, at most 50 characters. No person, company or tool names: the disclosure rules apply, and a `claude/` prefix is tool attribution. An agent renames a generated branch before its first push.
- **One branch per pull request,** deleted after merge.
- **Traceability lives in the pull request.** Rebase merges leave no merge commit, so the branch name is gone from history once merged. A spec pull request names its spec folder in the title or the first line of the body.

## Enforcement, in layers

Each layer covers a gap the one before leaves open. Steps 1 to 4 are needed from the first commit; steps 5 and 6 come with the GitHub repository and the first pull request. Steps 1 to 4 give fast local feedback; step 6 is what makes the rules binding for everyone.

### Step 1. Stop the trailer at the source

Commit `.claude/settings.json` with the attribution turned off, so every Claude Code session in this repository stops adding `Co-Authored-By` and "Generated with Claude Code":

```json
{
  "attribution": { "commit": "", "pr": "" }
}
```

`attribution` is the current setting; `includeCoAuthoredBy` is deprecated. Reference: https://code.claude.com/docs/en/settings-reference.md

### Step 2. Keep the rules in view

- Create `docs/commit-guide.md` with the rules above, plus five right and wrong examples for messages and one for splitting a mixed change into two commits.
- Add a short "Commits" section to the root `AGENTS.md` (which `CLAUDE.md` imports with `@AGENTS.md`), no more than six lines:

  ```
  ## Commits
  - Conventional Commits, `type(scope): subject`, subject only, under 72 characters, imperative, lowercase after the colon, no period.
  - No trailers or tool attribution. Describe the change, not the reason. Disclosure rules apply to messages.
  - One task, one commit, one concern; checks pass before every commit.
  - Branches: `NNN-slug` for a spec, `type/scope-slug` otherwise; no tool prefix. A spec pull request names its spec.
  - Stop after each task and propose the message; the maintainer commits or approves.
  - Full rules and examples: docs/commit-guide.md. A hook rejects messages that break them.
  ```

### Step 3. One checker, used everywhere

Write `tools/commit-rules/check-message.mjs` (Node, no new runtime dependency). It reads a message from a file path or from stdin, prints every broken rule, and exits non-zero on any failure. It checks:

1. The header matches `type(scope): subject` or `type: subject`, with an allowed type and, when present, an allowed scope.
2. The header is under 72 characters, the first letter after the colon is lowercase, and there is no trailing period.
3. The body, when present, is separated by a blank line and is at most two lines.
4. No trailer lines: nothing matching `Co-Authored-By:`, `Signed-off-by:`, `Generated with`, `Generated by`, or a model or tool name followed by a version.
5. No term from `.disclosure-terms.local`, matched case-insensitively, when that file exists. Without it the check is skipped, with a notice.
6. Merge and revert messages created by git pass through unchanged.

A second entry point, `tools/commit-rules/check-branch.mjs`, takes a branch name and checks it against "Branches and pull requests": the `NNN-slug` or `type/scope-slug` pattern, the length, and the disclosure terms. `main` and `changeset-release/*` pass unchanged.

Add `tools/commit-rules/check-message.test.mjs` and `check-branch.test.mjs` with passing and failing examples for each rule, run with the repository's test runner.

### Step 4. Block bad commits for agents and people

1. **Git hooks, committed in `.githooks/`:**
   - `commit-msg` runs the checker on the message file, so a fix costs one retype.
   - `pre-commit` runs the affected quality checks (for example `nx affected -t lint test typecheck`, and the token check when token files change).
   - `pre-push` runs the checker on every outgoing commit, catching commits made before the hooks were enabled, and runs the branch check on the pushed branch.
2. **Switch the hooks on automatically:** a root `package.json` script, `"prepare": "git config core.hooksPath .githooks"`, so every `npm install` enables them in that clone.
3. **Claude Code hook** in `.claude/settings.json`, so an agent's commit is checked even before git runs, and the agent receives the reason:

   ```json
   {
     "hooks": {
       "PreToolUse": [
         {
           "matcher": "Bash",
           "if": "Bash(git commit *)",
           "hooks": [{ "type": "command", "command": "node tools/commit-rules/claude-pre-commit.mjs" }]
         }
       ]
     }
   }
   ```

   `claude-pre-commit.mjs` reads the hook input from stdin, takes the command from `tool_input.command`, extracts the message (`-m` values or a heredoc), runs the checker, and exits with code 2 and the list of broken rules on stderr when it fails. If it cannot extract the message, it lets the command through and leaves the check to the `commit-msg` hook. Project hooks also apply to subagents. Reference: https://code.claude.com/docs/en/hooks.md
4. **Block the bypass:** add permission deny rules in `.claude/settings.json` for `Bash(git commit --no-verify*)`, `Bash(git commit -n *)` and `Bash(git push --no-verify*)`.

### Step 5. Backstop before anything reaches `main`

- **CI:** a job on every pull request that runs the checker over every commit in the pull request, and fails the pull request when one breaks a rule. The same job runs the branch check on the head branch and, for an `NNN-slug` branch, checks that the title or the first line of the body names `specs/NNN-slug`. This covers clones where the hooks were never enabled. Add it to the "changeset, API diff and docs" gate, so the gate count stays at seven.
- **Optional:** commitlint with `@commitlint/config-conventional`, configured with the same types, scopes and limits, if an off-the-shelf tool is preferred for the header rules. The trailer and disclosure checks stay in the custom checker either way.

### Step 6. Make the rules binding for every contributor

The local layers only help people and tools that use them: `.claude/settings.json` applies only to Claude Code users, and a Claude Code user's own local settings can override it; git hooks are off until `npm install` runs and can be skipped with `--no-verify`; the disclosure term list is never committed. Only checks that GitHub enforces reach everyone.

1. **GitHub ruleset on `main`:**
   - Changes only through pull requests.
   - The commit-message check from step 5 is a required status check.
   - Force pushes are blocked, and history stays linear.
   - The ruleset applies to administrators too, unless a written reason says otherwise.
2. **Merge method:** allow rebase merges only, so each atomic commit and its checked message land unchanged. If squash merges are ever allowed, GitHub writes a new message from the pull request title, so the pull request title must pass the same checker as a second required check.
3. **Disclosure terms in CI:** store the real term list as a repository secret, for example `DISCLOSURE_TERMS`, one term per line. The CI job writes it to a temporary file that the checker reads, and never prints it: failures name the commit and the rule, not the term. The disclosure rule then covers every contributor's commits, not only commits made on the maintainer's machine.
4. **`CONTRIBUTING.md`:** one short page for people, covering:
   - The commit rules, pointing to `docs/commit-guide.md`.
   - Running `npm install` once to switch the hooks on.
   - That CI rejects a pull request whose commits break the rules, whatever happened locally.
   - That the history is never rewritten after publication.
5. **Other agents:** Copilot, Cursor, Codex and other agents read `AGENTS.md` and are stopped by the git hooks and CI, not by `.claude/settings.json`. Keep every rule in `AGENTS.md` and the checker, and never only in Claude Code settings.

## What checks cannot enforce

- **Atomicity.** A check cannot tell whether a commit holds one concern. The workflow keeps it: the agent stops after each task and proposes one message per concern, and the maintainer or the reviewer subagent confirms before committing.
- **"Describe the change, not the reason."** A check can only catch known terms. Reviewing the proposed message is the real safeguard.

## Done when

- A commit with a `Co-Authored-By` trailer is rejected, by the Claude Code hook and by the `commit-msg` hook.
- A message over 72 characters, with an uppercase letter after the colon, a trailing period, an unknown type or scope, or a three-line body is rejected, with the rule named.
- A message containing a term from `.disclosure-terms.local` is rejected, and `.disclosure-terms.local` does not appear in `git ls-files`.
- `git commit --no-verify` is refused when an agent tries it.
- Pushing a branch named `claude/some-work` or `Feature_X` is rejected with the rule named; `001-nx-workspace` and `fix/tokens-dark-contrast` pass.
- A pull request from an `NNN-slug` branch that does not name its spec fails CI.
- After a fresh clone and `npm install`, `git config core.hooksPath` prints `.githooks`.
- A pull request containing a bad commit fails CI.
- A Claude Code commit in this repository has no attribution lines.
- The checker's tests pass, and every commit made while setting this up follows the rules.
- A direct push to `main` is rejected by the ruleset, including for administrators.
- A pull request with a bad commit cannot be merged: the commit-message check is required.
- Only rebase merges are enabled; if squash merges are enabled, a pull request with a bad title cannot be merged.
- A test commit containing a disclosure term fails CI, and the job log does not show the term.
- `CONTRIBUTING.md` exists and links `docs/commit-guide.md`.
- A commit made without Claude Code and without the hooks enabled is still stopped by CI before it reaches `main`.
